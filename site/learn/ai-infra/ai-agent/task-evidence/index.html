拆解问题，逐项核对 Agent 的证据

用两跳检索和逐项证据表，发现漏答、未读引用与原文不匹配，再人工判断结论。

教程AI AgentPython证据核对多跳检索
开始自测
本篇的学习目标把用户问题拆成可检查的子问题，补齐资料缺口，区分原文匹配与语义支持。
建议先读让 Agent 可停止、可回放、可验证

读完这一篇，你能把一个复合问题变成逐项核对的要求，用两次相互依赖的检索补齐资料，并解释为什么“每项都有原文”仍需人工判断。

前三篇的程序会检查引用 ID 是否来自已读资料。现在用户问：“示例站点发布前检查什么？链接检查失败以后，怎样恢复？”如果 Agent 只回答第一句，即使引用完全合法，也没有完成整个问题。把回答写长，不能补上没有检查过的要求。

这一篇继续使用同一个配套项目，新增 evidence.py 与 evidence_cli.py；前三篇的命令和两个只读工具继续可用。运行基线仍为 Python 3.11+、标准库和本机终端。

先把用户要求变成可检查的子问题

任务拆解是把一个需要完成的目标分成若干可分别检查的要求。这里先由人确定两个子问题，再交给模型选择搜索和读取动作。这样可以先检验“每一项有没有被回答”，而不把模型临时列出的计划直接当成用户要求。

evidence_cli.py 中的任务契约如下。id 给要求一个稳定名字，供结果配对；question 是这一项需要回答的内容。

最终报告必须恰好包含 checks 和 rollback 各一次。写“我会查找恢复方式”只能描述计划，不能让 rollback 变成已完成。必须提供结论及其资料，或者明确留下缺口。

子问题需要的结果不能代替结果的内容
checks示例约定中的发布前检查项目与原文“准备检查”这样的未来动作
rollback示例约定中的恢复方式与原文，或缺少资料只重复第一项的检查清单

这里没有实现一个自主规划器。如果以后让模型提出子问题，仍要核对它有没有删除、改写或遗漏用户要求。本篇把要求固定下来，重点观察模型执行与宿主核对之间的关系，也不要求模型公开内部推理。

用已读资料决定下一次查什么

配套资料是两条原创教学记录。第一条题为“示例站点发布检查”，正文为：

构建后先运行输入边界测试，再检查目标路径的内部链接。链接检查失败时，继续检索“恢复约定”。这是一组教学用约定。

第二条题为“恢复约定”，正文为：

链接检查失败时停止上线，恢复上一份已验证的静态产物，再复查内部链接。这是示例站点的约定，不代表所有系统。

第一次按“发布”搜索，只找到第一条。全文里的“恢复约定”提供了下一次检索的关键词；再搜索这个词，才找到第二条。这叫两跳检索：后一次搜索使用前一次取得的信息，解决第一批资料尚不能回答的部分。

模型轮次回放中的请求或结果此时能知道什么
1search_notes(query="发布")第一条记录的 ID、标题和短摘录
2read_note(id="release-policy")检查要求和“恢复约定”线索
3search_notes(query="恢复约定")恢复记录的身份，或没有结果
4read_note(id="rollback-policy")恢复约定的全文
5返回逐项报告提交两个结论及原文供核对

搜索仍然是子串匹配，最多返回三条，并非语义搜索。“恢复约定”出现在正文里，只提供与当前问题有关的检索线索；正文即使要求执行命令，也不能改变工具白名单。全过程仍只有搜索和读取两个动作。

默认离线模式把上述请求预先写在 data/evidence_replay.json，用于重现消息通路。真实模型可以选择不同关键词、合并请求，也可能提前结束或查错资料；固定回放没有展示自主选择能力。

只把本轮成功读取的全文放入账本

已读账本是一份只存在于本次运行内的字典：键是资料 ID，值是成功读取的记录。它让核对器知道模型实际取得过哪些全文。搜索结果只说明找到一条记录，不算已经读到可引用的原文。

每次 investigate(...) 都创建新的 ReadLedger。上一轮读过的资料不能让下一轮的虚构引用通过。本篇的账本不是长期记忆，也不会写进轨迹文件；原来的轨迹继续只保存工具名、调用 ID、轮次和状态等元数据。

逐项检查原文，再把语义判断交给人

模型最终提交 JSON 报告。JSON 用对象和数组表示结构，宿主通过标准库 json.loads 解析，再逐项检查；提示词要求某种格式，并不能保证模型一定遵循。下面是一个子问题的完整结果项：

外层报告为 {"items": [...]}，数组中包含两个这样的任务项。state 是模型自己填写的证据声明：supported 表示它声称有依据，不是宿主已经判定正确。claim 是待核对结论，note_id 标明资料，quote 保留其中一段连续原文，不添加旧回答格式的方括号引用。

核对函数 audit_report(text, tasks, reads) 接收报告文字、用户任务与本轮账本，返回核对状态、匹配原文的任务数、缺口 ID 和错误代码。它分两步检查。

第一步检查结构：报告最多 16000 个字符，顶层只有 items；任务数必须相同，每个预定 ID 恰好出现一次，不能出现额外字段。JSON 重复键也被拒绝，避免同一个字段前后写两种值而悄悄覆盖。supported 必须有非空结论和 1–3 段证据；找不到资料时使用 missing，结论为空字符串，证据为空数组。只写一个检查结论而漏掉恢复项，会得到 invalid_report。

note_id not in reads 拒绝没有成功读过的记录；quote not in ... 要求引文是正文中逐字相同的连续片段。它会拒绝模型擅自改写的“引文”，也不会把标题或摘要当作已读全文。程序还要求引文有非空白内容且不超过 800 个字符，但没有据此判断原文是否足够相关。

覆盖数 covered 只计“该项结构合规且全部引文匹配”的任务，不是任务成功率。即使引文真实，一句断章取义的片段也可能支持不了模型结论。

核对状态含义下一步
needs_review每项有结构合规、匹配已读原文的证据人工核对结论、条件和相关性
evidence_gap至少一项明确声明没有证据，其余项通过机械检查保留缺口，再决定是否扩充资料或追问
invalid_report漏项、重复项、格式错误、未读引用或引文不匹配修正报告或执行过程，不能当作已答完整
run_stopped循环因预算、协议、网络或其他停止原因没有提交可审报告先处理对应运行状态

missing 只表示这一次没有交付证据，不证明所有资料中都不存在答案。程序也没有检查模型是否充分搜索。看到 evidence_gap 时，应先分清资料缺失、关键词不合适和检索预算不足，而不是直接补写一个猜测。

新的核对入口复用旧循环，不改动前三篇的 complete 规则：

JSON 报告使用 note_id 字段，通常会被旧的方括号检查标为 unverified_answer；新入口对这种已经提交最终文字的响应另做核对。预算或网络停止则直接返回 run_stopped，不会被转换成证据成功。两层状态各自回答不同的问题，不覆盖原结果冒充通过。

完整程序：证据账本与核对入口

把以下内容保存为配套项目的 evidence.py；它依赖同目录已有的 agent.py 和 tools.py。CLI、公开数据、回放和测试都在源码下载包里，evidence_cli.py 调用本文件的 investigate。

真实模式还有一个输出契约需要调整：前三篇的模型指令要求方括号引用，本篇要求 JSON。evidence_cli.py 的 EvidenceResponses 继承原适配器，用一个运输函数包装器替换每次请求的 instructions，继续复用原有 HTTP、错误处理与预算；原适配器的默认行为保持。transport 接收请求字典、密钥和超时，包装器设置指令和需要返回的附加项，再交给原函数。

这里通过指令请求 JSON，最终仍由本机核对器解析；没有新增服务端格式保证。原适配器使用 store=False，新入口显式请求 reasoning.encrypted_content，让需要这类状态的模型返回供下一轮继续传递的不透明项。循环保留它，但不解密、不打印到报告或轨迹。接口核对日期为 2026-10-17，模型是否可用仍由自己的账户决定。

已有前文模型环境时，可以在本机显式运行 python3 evidence_cli.py --live --show-report，再尝试加 --case missing。这会沿用原有模型适配器，只把两个问题与实际读取的公开教学资料交给服务；网页仍只提供阅读和下载。模型可能输出围栏、漏项或改写引文，核对器会报告失败而不自动无限重试。离线 wrong-claim 反例不适用于真实模式。

任务要求、执行证据和结论分别核对

固定的两个子问题防止回答只覆盖容易的一半；读取结果为后续搜索提供线索；本轮账本让引文绑定到实际成功读过的全文。逐项报告把有依据的声明和没有依据的缺口摆在一起，让下一步行动有明确对象。

核对器完成的是身份、结构与连续原文检查。它把合格报告交给人判断，把缺资料和运行中断明确留下；它没有替模型生成计划，也没有自动证明结论。长期记忆、写入审批和中断恢复仍是后续独立实现内容。
