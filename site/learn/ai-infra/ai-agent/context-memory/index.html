管理上下文与记忆：给 Agent 留下必要的线索

比较完整历史与短摘记，亲手实现带来源、可撤销的会话记忆，并检查压缩丢失了什么。

教程AI AgentPython上下文管理会话记忆
开始自测
本篇的学习目标区分一次请求的上下文与宿主持有的记忆；选择、撤销和校验摘记，在新问题中重新取得证据。
建议先读拆解问题，逐项核对 Agent 的证据

读完这一篇，你能为已经完成的问答保存一段有来源的短记忆，撤销它，并通过实验区分“上下文变短”和“保留了所需信息”。继续使用配套项目，运行基线为 Python 3.11+、标准库和本机终端。

第 4 篇已经能逐项核对证据。接下来用户追问：“链接检查失败后具体怎样恢复？”如果把上一任务的所有消息、工具结果和重复背景都带过去，程序可能还没调用模型就触发输入上限。只保存一条简短结论，又可能丢掉查找资料所需的线索。

本篇增加的是同一个进程内、跨独立问题的会话记忆。它不会自动写文件，也不让模型调用新的记忆写入工具。选择保存什么由宿主明确完成，进程退出后记忆不保留。

完整历史为什么会挡住下一次提问

上下文是模型生成当前响应时收到的信息。用户问题、此前的消息和工具观察都会占据输入空间；宿主内存里有一份记录，不表示模型本轮已经看到了它。记忆簿则是宿主持有的较小记录，只有被选入当前请求的内容才成为这次上下文。

先运行会超限的对照：

程序先完成上一节的公开固定回放：5 轮、4 次工具调用，并成功取得两条资料。准备阶段只给第一条记录追加重复背景，不改变检查要求与恢复线索。这个回放已经结束，接下来才开始一个独立的新问题。

full 把旧任务的整份公开回放作为一段低信任数据附在新问题后。本例初始输入为 5683 个字符，超过设定的 2200 字符，输出包含：

新问题尚未调用模型或工具，退出码为 1。输出中的 current_turns 与 current_calls 只统计新问题；准备回放仍消耗了前面明确列出的轮数和调用，不能把这些工作当作没有发生。

这里的字符数沿用原执行器的计量：把输入消息列表用 json.dumps(..., ensure_ascii=False) 序列化后，计算 Python 字符串长度。它包含消息表示中的括号、字段名和转义字符，不包含工具声明、模型指令等完整请求开销。2200 是本地实验的输入限制，不是模型 token 窗口，更不能换算成精确费用。

把查找线索摘出来，保留它来自哪里

上一任务读到的第一条资料包含一句：“链接检查失败时，继续检索‘恢复约定’。”实际保存时保留原文中的中文双引号，不改写内容。这句话不能直接回答恢复步骤，却保留了下一次搜索需要的名字。

本篇采用摘取原文的压缩方式：从较长记录中明确挑选一段，不让模型自动生成摘要。MemoryEntry 记录自己的 ID、资料 ID、原文和来源版本：

memory_id 标识这一次摘记，note_id 标识来源资料，二者不是同一个身份。source_sha256 是宿主用来源的 ID、标题和全文计算的内容哈希；正文或标题变化时，可以据此排除旧摘记。哈希只能检查内容版本是否相同，不能判断资料是否真实可靠。

MemoryBook.remember 接收先前成功读取的字典、资料 ID 和选中的引文，返回新记忆 ID：

先查资料是否属于给定的成功读取集合，再复用 Notes 核对记录结构；随后要求引文是原文中的连续片段，有非空白内容且总长度不超过 200 个字符。它不能凭空把一句生成的结论登记成原文。

每条摘记通过后才写入字典并递增 ID。默认最多保存六条；容量满时报错，原有记录继续保留。代码没有擅自删除最旧的一条，因为“最旧”并不等于“最不重要”。在这个小实验里，保存和撤销策略由调用方明确选择。

用短记忆开始新问题，完整保留当前调用链

默认 compact 只把当前可用的短摘记带入新问题：

主要输出变为：

这次初始消息装得下。固定回放从摘记取得“恢复约定”这个关键词，依次搜索、读取恢复记录，再提交逐项报告。最终证据来自本轮的 read_note，不是来自记忆里的旧内容。

question_with_context 在当前任务要求后附加低信任数据。这个函数不把记忆升级为系统指令：

build_question([task]) 复用上一节的任务契约：本轮只有 rollback 一项要求，仍须提交结论和原文，或明确报告缺口。context 可以是完整旧回放，也可以是短记忆，两种输入经过相同的字符预算与证据核对。

answer_question 每次创建新的 ReadLedger，随后调用原来的 run。旧记忆中的资料 ID 不自动进入新账本。如果模型没有重新读取，仅复制摘记当作本轮引用，核对器会报 unread_note。

这里有一个明确的压缩边界：旧问题已经结束，宿主才选取摘记并建立新问题。新问题运行期间，每个工具请求、对应观察与必要的不透明状态仍按原规则完整保留。不能简单切掉消息列表的前半段，留下一个找不到对应请求的工具结果；也不能在预算不足时悄悄重启同一任务、清零计数继续。

短记忆只是让初始输入更小。新问题中的工具结果仍可能继续增长，每轮都执行原预算检查；如果再次超限，程序明确停止。本篇没有实现任意时刻的自动摘要或原地删减。

来源变化和撤销怎样影响下一次请求

选择进入上下文的记录时，select(records) 接收当前资料列表，返回可用摘记和过期记忆 ID：

它重新计算当前记录的哈希。资料被删除、标题或正文发生变化，都会让该摘记进入 stale，本次不会将其文字发给模型。代码没有自动重写旧摘记；需要调用方决定是否重新读取并保存新版本。

实验只在第一条来源正文后追加“修订。”，即使恢复线索仍然存在，整个记录的版本也已经变化。因此 stale_memories 为 1。这种做法比较保守：它可以发现与登记版本不一致，却不会智能判断这次改动是否影响引文含义。

手动撤销更直接，使用记忆 ID 删除该项：

撤销后的 select 不会返回这段文字，后续请求因此没有它。撤销影响的是以后构造的请求，不能收回已经发送给模型服务的数据，也不能使调用方先前拿到的 Python 副本消失。当前实现只管理这个进程内的字典，不声称提供持久存储、物理擦除或跨进程恢复。

在这两个固定回放中，新问题不再得到恢复线索，按“恢复方式”搜索后提交缺口，状态为 evidence_gap、覆盖 0/1、2 轮与 1 次工具调用。它们展示的是程序在这些指定请求下的行为。真实模型可能改换关键词或重新查找第一条资料，不能据此断言撤销一条摘记就一定无法回答。

变短以后，还要检查有没有丢掉关键内容

最后一个对照只改变“选哪句原文”，保留记忆簿和版本检查的全部规则：

这次保存“构建后先运行输入边界测试，再检查目标路径的内部链接。”它确实来自读过的原文，也没有过期，初始输入只有 584 字符。但这句话没有保留“恢复约定”这个名字，固定回放最终报告 evidence_gap。

情形新问题初始输入字符可用的恢复线索本例结果

所以压缩需要两个独立检查：输入是否装得下，以及保留的信息是否帮助当前任务。原文完全真实，也可能选错了重点。这里的摘记由人选择，回放分支预先写定；这组数字检查程序输入和行为，不是模型检索准确率或压缩质量排行榜。

运行全部回归检查：

测试覆盖容量满时保留旧记录、引文必须来自成功读取、撤销后不再发送、来源变化排除、返回视图不修改记忆、活动工具链与不透明项完整，以及记忆不能冒充本轮读取。还检查预算不足时停止，不通过删除某条观察来“挤过”限制。

完整程序：会话记忆与新问题入口

以下保存为配套项目的 context_memory.py，依赖已有 agent.py、evidence.py 和 tools.py。命令入口 context_cli.py、公开回放与测试均在下载包中；该入口在同一个进程内完成准备、摘记、撤销或版本检查，再调用这里的 answer_question。

已经配置前文模型环境时，可以在本机显式执行 python3 context_cli.py --live --show-report。准备阶段仍使用公开固定回放，只有新问题使用真实模型。它将当前问题、可用公开摘记及本轮读取的资料发给服务；网页仍只提供阅读和下载。

ContextResponses 沿用原 HTTP 适配器，为每一轮指定报告格式和低信任数据规则，并请求需要继续传递的不透明输出项：

当前用户任务留在输入消息中，旧摘记也作为其中的数据存在。适配器不把摘记放进 instructions；提示词规则不能替代宿主的工具白名单和参数验证。reasoning.encrypted_content 沿用上一节的无存储会话方式，在当前调用链中保留，不解密、不打印为报告或轨迹。接口核对日期为 2026-10-17。

真实模型可能使用不同检索词，也可能误用记忆或输出错误格式。需要另外记录实际任务、模型、调用轨迹、用量与人工判断，才能评价这种上下文选择是否帮助了它。固定回放没有代替这组实际试验。

小结：保存线索，重新读取，明确遗忘

本篇把完整历史和短记忆分开：宿主从已读公开原文中摘取线索，记录来源版本；开始新问题时选择仍有效的摘记，并重新读取需要引用的资料。这样既能减少初始消息，也保留了证据检查的边界。

容量、版本和撤销回答的是“哪些记录还可以进入下一次请求”，不是“结论是否正确”。压缩之后仍要观察遗漏的条件和线索；本篇的会话记忆不跨进程保存，写入审批与持久恢复继续按后续节点分别实现。
