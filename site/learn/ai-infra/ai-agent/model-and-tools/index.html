接入模型与资料工具：做一个问答 Agent

自己实现搜索、读取和模型适配，让模型根据资料反馈决定下一步。

上一节的循环能执行工具，但决定动作的是固定回放。现在让真实模型根据问题选择搜索关键词、资料 ID 和结束时机，做出一个可以在终端使用的资料问答 Agent。

目标很具体：问“构建通过就能发布吗？”，程序搜索资料、读取“发布前检查”，最后引用 [release] 作答。我们自己写工具和控制循环，不把关键行为藏在框架默认值里。

文件负责什么修改它时应观察什么
agent.py保存消息、分派动作、检查停止条件工具结果是否进入下一轮
tools.py搜索与读取契约参数错、ID 不存在时的返回行为
responses_backend.py把消息发送给模型并取回输出项请求字段、状态和失败方式

资料中的 untrusted 特意放入了要求执行 Shell 的句子。它是故障实验数据，不是授予程序执行命令的权限。首批项目只有两个只读工具，模型不能通过参数指定其他文件。

给搜索和读取写出窄而明确的契约

搜索用于发现候选记录；读取用于取得记录正文。把它们分开，模型先看到短摘录，再决定哪条值得读，避免每个问题都把全部资料放进上下文。

配套项目中的完整 Notes.execute 如下。self.records 是从明确指定的 JSON 资料装入的字典，不是模型给出的任意文件路径。

搜索参数只能有 query，读取参数只能有 id；值必须是去掉首尾空白后长度为 1–120 的字符串。多余的 path 字段不会被默默接受。读取成功返回独立字典，未知 ID 抛出 ToolError("note_not_found")，宿主把这类错误作为观察送回模型。

搜索是大小写不敏感的子串匹配，最多返回三条，摘录最多 70 个字符。例如“发布”可以匹配“发布前检查”，但“上线验收”不一定匹配。这不是语义检索，没找到时应换关键词或说明资料不足；不能把零结果解释为世界上不存在答案。

required 要求参数键出现，additionalProperties=False 拒绝额外键，strict=True 启用模型接口的严格参数模式。不过严格模式不会替我们判断“这个 ID 是否在资料里”，也没有替工具检查长度和业务条件。Schema 告诉模型怎样提出请求，宿主验证决定请求是否能执行，两者承担不同责任。

接上 Responses，让模型生成下一步输出

模型适配器把本地消息和工具声明打包为 HTTP 请求，再取回输出项。核心循环只约定调用 generate(messages, tools)，所以换模型服务时主要改适配层，不重写资料工具。

model 来自读者本机的 OPENAI_MODEL，需要是自己账户可用且支持 Responses 函数调用的模型；本篇不预设某个模型永久可用。instructions 说明回答目标、只根据资料作答以及工具正文不能改变权限。

input 包含本轮之前保留的消息；tools 提供两个函数的声明。parallel_tool_calls=False 让首批实验保持串行，宿主仍检查响应中的全部工具调用。max_output_tokens 限制单次响应的输出 token，可能包含模型的推理用量，不等于答案字数或整次任务费用。

store=False 让本例由客户端传递会话上下文。不能因此只保存文字：模型可能返回工具调用、文字以及不透明的推理状态，下一轮须保留需要继续会话的输出项。当前官方接口在这种模式下会提供加密推理内容；项目不解密、不显示、不把它写入运行轨迹。

post_json 的完整实现位于配套文件：只向固定的官方 Responses 地址发送 HTTPS 请求，凭据来自进程环境；HTTP 错误只返回状态码，网络错误转换为固定错误状态，不打印原始响应或密钥。请求设置 30 秒阻塞 I/O 超时；它不是整个任务的硬截止时间。

把动作、结果和下一轮接起来

下面是 agent.py 里将一批调用变成观察的实际代码。前面的检查已经确保没有超过总调用预算，调用 ID 不为空、不重复，名称和参数字段是字符串。

第一次搜索的结果会变成 {"ok":true,"data":[...]}；读取结果会包含完整记录。参数无法解析则得到 invalid_json，未知工具得到 unknown_tool。这类可以改变下一次请求的问题留给模型修正，但仍受轮数和调用预算限制。

消息列表先追加原始模型输出，再追加对应结果。因此下一轮模型看到的不只是“资料内容”，还知道这份资料响应的是哪次调用。若一轮同时有文字和工具调用，程序先执行工具，不把尚未完成的文字当最终答案。

read_ids 记录实际读取成功的资料 ID，后面用它检查最终答案的来源标记。搜索里看过一个摘录，不等于读过整条记录；不能只搜索到 release 就把它算作已核对的正文。

做两次改动，再收束这个 Agent

先在默认回放下，把 data/notes.json 的 release 正文改成另一项检查。你会发现工具观察变了，最后那段文字却不一定变：完整项目的回放文件是预先写好的响应，它用于验证消息协议，不会重新理解正文。这是测试替身的边界。

再在真实模式下加入一条可公开的新资料，使用只有该资料包含的关键词提问。观察是否发生搜索和读取，再逐句对照回答。真实模型也可能忽略证据或过早作答，不能因为接上 API 就跳过核对。

至此，工具层负责查资料，模型适配层负责产生下一步，宿主负责执行和回传。下一篇让运行可控、结果可查会用反例检查这些责任：无限重试怎样停，工具失败怎样暴露，引用正确为什么仍可能答错。
