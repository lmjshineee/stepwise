流与可靠输入：为什么后面的数字没有读进去？

从一次停在 stop 的求和开始，区分读取位置、错误状态、整行与字段，再检查文件和格式化输出。

课程C++C++23CS106L输入输出错误处理
开始自测
本篇的学习目标能解释解析停止和空行，按输入契约恢复，检查文件写入结果。
建议先读引用与初始化

输入明明是 10 20 stop 30，程序却只加到 30。最后那个 30 没有消失：程序在 stop 处读不出整数，停止继续读取了。

本篇先把这件事拆成“当前读到哪里”和“上次读取是否成功”，再处理空行、文件与输出。示例使用 C++23 模式；std::println 是 C++23 引入的直接格式化输出接口，定义在 <print>，自动加换行。它让输出更简洁，输入仍由流负责。

先让读取结果决定是否继续

求和为什么停在 30

std::istringstream 定义在 <sstream>，把字符串当作输入源。这样无需反复敲键盘，就能检查同一段数据。input >> value 尝试读一个整数，成功后才使用 value。

保存为 read_loop.cpp，执行 clang++ -std=c++23 -Wall -Wextra read_loop.cpp -o read_loop，再运行 ./read_loop，输出：

10、20 先后读取成功；stop 不能解析成整数，流设置失败状态，循环条件为假，因此还未读到后面的 30。后续完整程序也用同样的命令编译，替换文件名即可；需要实现 <print> 的标准库，语言模式本身不会补齐库实现。

先定输入约定，再写恢复策略

如果输入约定“全部都是整数”，遇到 stop 应报错；如果允许夹杂可跳过的单词，就需要移走它再继续。是否恢复由业务约定决定，不能看到失败就无条件忽略。本文求和的数字与总和都约定在 int 可表示范围内。

换一个来源，复用同一个读取判断

把字符串输入换成 std::cin 或文件输入流，while (input >> value) 的含义不变：先尝试读取，再判断状态。可以先用固定字符串复现错误，再连接真实输入源。

标准流分别连接哪里

<iostream> 提供 std::cin、std::cout、std::cerr、std::clog。它们分别是标准输入、标准输出与两个标准错误输出对象。cerr 默认设置 unitbuf，请求在输出操作后刷新；clog 默认没有该标志。名字并不规定业务错误的严重等级。

位置与状态是两件事

可以把流想成一条传送带，读取位置指向接下来处理的字符，状态则像记录上一次操作结果的指示灯。clear() 重置指示灯，不会把传送带上的坏字符拿走，也不会回到开头。标准流主要为字符序列提供接口；网络套接字需要额外适配，不能直接认为所有设备都已经有标准流接口。

输出运算符为什么可以连写

std::cout 是对象。std::cout << "sum: " << sum 先输出前缀，再使用返回的同一个流引用输出数字。std::endl 既换行又请求刷新；只需分行时用 '\n'。刷新不等于文件内容已持久化到磁盘。

提取一个值，不等于验证整段文本

格式化提取默认跳过前导空白。读字符串通常在下一处空白前结束；读整数则按数字格式消耗字符。12x 可以先被读成 12，留下 x。若要求整个字段只能是整数，后面还需要检查是否存在未消费的字符。

不要写 while (!input.eof()) 后再不加判断地使用读取结果：EOF 信息由读取操作更新，格式错误也可能在到达末尾前发生。循环条件应放实际的读取操作。

区分一个字段和一整行

std::getline(input, line) 定义在 <string>，读取到分隔符，消耗分隔符但不把它放进结果。默认分隔符是换行。数字提取往往把行末换行留在输入中，紧接的 getline 因而可能得到空字符串。

清除标志后，还要移走坏字段

下面的约定很窄：输入由空白分隔的小整数和纯字母坏单词组成，总和不越界。允许跳过 stop，再继续读后面的数。

输出 skip: stop 和 sum: 60，各占一行。失败时 stop 还在输入里；clear() 之后才能再提取字符串，把坏字段移走。只清标志会在同一单词反复失败；直接丢弃整行则连后面的 30 一起丢掉。本例不是通用的越界恢复器，也不会把 12x 当作一个整体拒绝。

选读：EOF 不一定代表这次读取失败

eofbit 表示读取触及末尾，failbit 表示所需提取未成功，badbit 表示底层严重错误；不要依赖这些位的具体数值。流的布尔检查相当于 !fail()，而 fail() 同时检查 failbit 与 badbit。最后一个整数可能读入成功且只设置 eofbit，仍应处理它；下一次提取才失败。

默认流异常掩码不因这些状态位抛异常。可以用 exceptions(...) 配置失败抛出 std::ios_base::failure，但调用本身也可能因已有状态触发异常。选用状态分支或异常时，要让调用者知道错误怎样返回。

文件、字符串与打开模式

输入接口是 std::istream，输出接口是 std::ostream；字符串流位于 <sstream>，文件流位于 <fstream>。双向的 std::stringstream 与 std::fstream 同时提供读写接口，输入位置与输出位置需要分别理解。

默认 ofstream 打开已有文件会截断旧内容。app 每次写入都移到末尾；ate 只在打开时移到末尾，之后还可移动位置；trunc 明确要求截断。构造时传文件名已经尝试打开，不必再立刻 open()。关闭后写入会失败；再次成功 open() 可以重置状态，但也可能按打开模式截断旧内容。

读取全部字节时，空文件也是成功结果

需要原始字节时，用二进制模式和 read，不要逐词提取：逐词读取会跳过空白。分块读取后用 gcount() 取得本次实际读取的字节数，最后一次不足一块的尾部也要追加。完成后检查 bad() 和是否正常到达 EOF。成功的空文件得到空字符串，打开／读取失败则走独立错误通道。

输出的格式，是否会影响下一次调用

流会保存一部分格式状态。先理解一个金额显示，再按需要展开细项；这些设置改变的是文本表示，不是原数值。

选读：进制、宽度、填充和精度

进制设置会保留

std::hex、std::oct、std::dec 分别选择十六、八、十进制。输出 90 时分别可得到 5a、132、90。切到十六进制后，后面的整数也会受影响，直到改回 std::dec。

宽度通常只作用于下一个字段

<iomanip> 中的 std::setw(4) 设置字段最小宽度，不截断更长的文本。它通常只影响下一次相关插入，随后宽度被重置，不能把它和一直保留的进制状态混为一谈。

填充字符与对齐方向

std::setfill('0') 改变宽度不足时使用的填充字符，并保持这一设置；std::left、std::right 控制对齐。std::setw(4) << std::setfill('0') << 7 在默认右对齐时输出 0007，再次输出不带 setw 的 8 则只是 8。

精度的含义取决于浮点格式

std::fixed << std::setprecision(2) 将 3.14159 显示为 3.14；在默认浮点格式中，precision 表示有效数字数量，而非固定小数位。输出只是显示，不把原来的 double 永久四舍五入为两位小数。

操纵符改变的是当前流

std::boolalpha 把布尔值显示为 true／false，std::noboolalpha 恢复数字形式。格式化函数如果接收调用者的流，应约定是否恢复 flags()、precision() 和 fill()；只恢复 flags 并不能恢复其他所有状态。

格式字符串让每次输出的意图更局部

std::format（C++20）返回格式化字符串，std::println（C++23）直接输出并换行。它们不用为这一行先改动 cout 的精度或填充设置。{:.2f} 表示按固定两位小数格式显示一个浮点参数，先看完整例子：

选读：为什么流接口既统一，又带有状态成本

基础阅读到这里已经可以处理输入与文件。下面讨论实现选择，遇到重载或库接口问题时再展开。

展开流接口与缓冲设计

格式与类型要一起匹配

C 的 printf／scanf 使用格式说明符，与实际参数不匹配可能造成错误，某些情况是未定义行为。流通过函数重载选择整数、字符串等操作；现代格式接口又提供格式字符串检查。不能由此推出任意输入都会自动合法。

统一设备接口的目标

同一段输出逻辑可接收 std::ostream&，由调用者选择标准输出、文件或内存字符串。这让内容格式与目的地分离；是否适合某个系统，还要看错误处理、编码与性能要求。

格式转换与字符缓冲分别负责什么

上层根据值的类型把数字变成字符，下层流缓冲负责取得或送出字符。解析失败可能发生在格式层，设备失败可能来自缓冲层，错误处理不能只看字符串看起来是否完整。

输入、输出与双向流的关系

basic_istream 与 basic_ostream 共享基本状态能力，basic_iostream 同时提供输入和输出。文件流、字符串流再连接相应缓冲。这是类之间的接口复用，不表示文件与内存的失败方式相同。

类型安全不等于业务校验

in >> int_value 选择整数提取逻辑，但“年龄必须在 0 到 150”仍需读取成功后自行判断。超出目标整数类型范围会设置失败状态；不能把任何失败结果都当作一个可信的数字使用。

用户类型可以提供自己的输出方式

可以为课程记录定义 operator<<，内部把已知字段交给现有输出操作。接收输出流引用并返回同一引用，才能继续链式调用；重载本身不要偷偷替调用者修改不相关的全局输出设置。

成员与非成员重载

流类已有成员重载负责许多内置类型，字符串和自定义类型常通过非成员重载接入。选择应根据实际重载集合，而非把所有 << 都解释成某一种成员函数调用。

连写依赖返回引用

(out << a) << b 的后半段继续操作前半段返回的流。返回值也让整段表达式可以再用于状态检查。输入同样可以写 if (in >> x >> y)，在两次读取都成功后使用结果。

为什么自定义插入通常放在类外

out << record 的左侧是流，不能通过给 record 增加成员函数来改变左侧流类。常用非成员函数接收流和 record；如果只用公开访问器，无需 friend，确需访问私有字段时再讨论授权。

语法选择服务于接口

运算符语法便于组合，但普通命名函数也能提供格式化接口。选择流、格式字符串或字符转换时，比较是否需要统一设备、局部格式、底层字节或严格数值转换，而不是给每种场景强行指定同一语法。

缓冲减少调用次数，但并不保证提速

缓冲可以把多次小写入合并。每行刷新可能破坏这个收益；实际速度仍取决于设备、库实现、数据量和测量方法，不能仅凭调用风格宣称快多少倍。

缓冲失败要向上报告

std::streambuf 提供字符传送的底层接口。它不能送出要求的字符时，上层流会记录失败；重试之前必须确定设备是否恢复，不能只清掉状态就声称输出成功。

关闭同步与解除绑定是两个开关

std::ios::sync_with_stdio(false) 控制标准 C++ 流与标准 C 流的同步；std::cin.tie(nullptr) 解除读取前自动刷新所绑定输出流的关系。交互提示可能因此需要显式刷新。改变同步应在标准流 I/O 前完成，混用 C 和 C++ 输出时还要自行管理顺序。

常见成本来自额外工作

反复构造解析器、每条记录刷新、重复分配与多余转换都可能增加成本。优化前先测量，保留错误检查；不要把删除失败分支称为可靠的性能优化。

把状态交还给调用者

接收流引用的库函数可以暂存需要改变的格式设置，结束时恢复；如果启用异常，还应使用在离开作用域时恢复设置的资源管理对象。不要假定只保存一项设置就足够。

地区与编码需要单独约定

locale 会影响某些数字与字符分类规则，窄字符流不会自动把任意来源解码成统一 Unicode 文本。机器协议、用户显示和二进制数据是不同的要求，应在接口中说明采用的格式和编码。

保留流接口的理由

需要兼容现有 ostream 重载、逐步读取或连接文件与字符串时，流仍然有价值。仅为得到一行局部格式化文本时，可以直接使用现代格式接口；二者可并存。

选读：严格转换、现代输出与检查清单

展开字符转换、现代输出与练习

字符转换：要求整个字段都是整数

std::from_chars／std::to_chars（C++17，<charconv>）在调用者给定的字符区间工作，用结束位置 ptr 与错误码 ec 报告结果。整数 from_chars 不跳过前导空白，也不接受开头的加号。成功读到数字前缀仍不等于整个字段合法，必须同时检查 ptr 到达末尾。

只有 42、-7 成功，其他字段打印 invalid。失败时不要使用 result，部分转换可能已修改它。to_chars 则写入给定缓冲并返回有效区间；成功时 ptr 也可能正好在缓冲末端，不能无条件写 *ptr = '\0'。

format：先得到文本

std::format（C++20，<format>）返回拥有结果的字符串。std::format("{:04}", 7) 得到 0007。它处理显示格式，不负责把输入文本解析成数字；不要把它和 from_chars 的方向混在一起。

print 与 println：直接输出文本

std::print／std::println（C++23，<print>）直接格式化输出，后者补换行。不指定目标时写标准输出，也有接收 C 文件句柄的重载；输出流重载由 <ostream> 提供。不要把这些接口说成必然没有内部缓冲或临时存储，输出错误仍需处理。

Ranges 不改变输入失败规则

Ranges（C++20，<ranges>）可把序列过滤、转换与遍历组合起来；基于流的视图同样受读取状态影响。若需要恢复坏字段或保留空行，应先写清输入协议，再选择显式循环或视图。视图、迭代器与 Lambda 的详细用法属于后续主题。

每种输入至少试一个失败例子

固定测试空输入、坏字段、数字前缀加垃圾、数值越界、有意义空行和最后一行没有换行。正常文件读通一次，不能证明解析边界都正确。

根据数据约定选择接口

按单词或数字连续读取用提取操作，保留行结构用 getline；严格数字字段用 from_chars 并检查结尾；格式化输出优先考虑 println／format，需要兼容既有流接口时继续使用 ostream。二进制协议使用明确长度的 read／write，而非依赖空白分隔。

短路条件与明确长度

if ((in >> x >> y) && x > y) 只有前面的两次读取成功后才比较数据。输出字节可以用 out.write(bytes.data(), count)，其中 count 为有效字节数；字节数组不需要靠零结尾确定长度，写完仍要检查状态。

把选型落到一个小任务

试做一个成绩读取器：每行包含一个整数，空行需报告，12x 需拒绝，合法范围为 0 到 100。先 getline 保留行边界，再严格转换整个字段，转换成功后检查范围，最后用 println 输出结果。不要因为数值转换成功，就省略成绩范围检查。

小结：读取结果、输入边界与恢复约定

先尝试读取，再根据结果决定是否使用数据。流的位置和状态分开变化：清除失败标志不会移走坏字段，也不会验证整段文本。是否跳过、丢弃一行或直接报错，要由输入约定决定。

需要保留行结构就用 getline，需要严格整数就核对 from_chars 的错误码与结束位置，再检查业务范围。文件打开、后续读写和关闭各有失败边界；输出格式改变的是显示，不能代替这些检查。
