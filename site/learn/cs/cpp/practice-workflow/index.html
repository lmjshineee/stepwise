从课堂代码到可维护的小程序

把 CS106L 代码与作业中的接口、失败边界和资源意识，落实到可构建、可测试的成绩解析项目。

教程C++C++23CS106L项目实践测试
开始自测
建议先读流与可靠输入从源文件到程序

打开一份课堂代码时，最容易做的事是把空缺补到能运行；更有价值的问题是：函数为什么这样接收参数，失败之后还留下什么，下一次改动怎样知道没破坏已有行为？CS106L 的课堂练习和七份作业，恰好不断把这些问题放到眼前。

这篇沿着“读取一行成绩，检查后输出”的小程序，把接口、数据边界、文件组织和测试连起来。示例是独立练习，不需要下载数据或第三方库。先读过流与可靠输入、类与值语义和构建流程，会更容易理解拆分的理由。

本篇使用 C++23 编译模式；std::optional、std::string_view 与 [[nodiscard]] 均从 C++17 引入。没有借用字符串的返回值，返回的记录拥有自己的姓名。

先看谁在调用，再决定接口怎样写

SimpleEnroll 作业要求结合调用处修改函数签名。它提醒我们：看见一个 vector，不能马上决定“都传引用”。读取课程表、筛选记录、删除已经处理的课程，对输入的要求不同。

如果函数只观察一份大容器，可以用 const std::vector<Course>& 借用它：const 表示不通过这条访问路径修改元素。若函数确实要删除课程，调用者必须看得出修改会发生。小整数通常直接按值传递；本来就需要一份独立副本时，也不该为了避免复制而改变语义。

先写一句调用者能检查的承诺，比先挑参数写法更有效。例如：“解析失败不产生记录；解析成功返回一条独立记录。”这样就不需要一边修改外部对象，一边让调用者猜哪部分已经有效。

从练习里遇到的事值得带走的判断放进自己程序时的做法
SimpleEnroll 读取和移除课程观察、生成结果、修改输入是不同职责从调用处写清输入、输出和允许的变化
Make a Class 分开声明和实现一个类型应有稳定、可解释的操作先确定合法状态，再决定成员与接口
Ispell 组合容器、算法和函数对象数据表示与处理规则可以分别变化让遍历调用小而明确的操作，不把所有步骤塞进循环
Treebook 调整复制与运算“复制后是否独立”是行为约定使用值类型时验证独立修改，拥有资源时追踪责任
Explore Courses 查询可能缺失的课程没找到应是正常、可表达的结果使用 optional 并在读取值之前判断
Unique Pointer 转移资源借用、拥有和转移有不同后果日常程序优先用标准资源管理对象，练习实现用于理解责任

这里没有要求把每次小练习都改造成一套架构。课堂代码允许集中展示一个特性；当你开始复用其中的函数，就要补上它原本没有承担的输入条件和失败行为。

先把一整行读明白，再交出结果

约定输入每行是“姓名 成绩”：姓名是一个不含空白的字段，成绩是 0–100 的整数，行尾不能再有其他字段。空行、缺分数、82.5、额外字段都算失败。失败时不输出半条记录，程序可以报告行号后继续处理其他行。

std::string_view 只借用本次调用期间的字符，不能让它指向的临时数据逃出函数。Record::name 则是拥有存储的 std::string；函数返回后，输入行改变也不会改掉记录中的姓名。[[nodiscard]] 提醒调用者检查返回结果，它本身不会在运行时阻止忽略。

完整文件：解析一行并返回记录

调用者只看到完整记录或缺失状态，不会接触局部记录的中间值。可以分别传入缺少分数、超出范围和多余字段的行，检查它们是否都被拒绝。

这是一行的提交边界，不是整份输入的事务。前两行合法、第三行不合法时，已经输出的前两行仍然保留。程序对这一点作出明确选择，才谈得上调用者能否依赖它。

完整文件：逐行处理与退出状态

optional（C++17）的布尔转换检查是否有值，record->name 则读取已经确认存在的记录。下游程序可分别接收标准输出、标准错误和退出码，不必从一串混合文本中猜测是否成功。

课堂的多文件例子让声明与实现第一次分离。搬进自己的项目时，还要保证“怎么构建”可以由文件表达，而不依赖你记得上次终端里输入过哪些命令。

给规则找反例，再把反例留下来

课堂单元测试的银行账户例子验证了正常存入和取款，却也邀请你检查负数。如果只判断“取款额不超过余额”，从 100 取出 −5 反而可能得到 105。测试通过说明已有样例通过；它不会自动替你决定负数应拒绝，还是属于另一种业务操作。

对这个解析器，先列输入与结果，再写检查。它不是把每行实现重复一遍，而是在约束“哪些输入被接受”和“返回值是否独立”。

require 在条件失败时抛出异常，测试入口把它转换成非零退出码。这样即使使用 Release 构建，这些检查也仍会执行；不能把可能被 NDEBUG 关闭的 assert 当成唯一的运行时测试机制。这里没有依赖下载测试框架，小项目也可以先把关键行为留下来。

同一份规则，链接到两个入口

score 是共享实现，score_demo 和 score_tests 各自拥有一个 main；不要把两个入口一起链接成一个程序。PUBLIC 让使用该库的目标也获得所需的语言特性要求。include(CTest) 在启用测试时生成测试配置，add_test 登记可执行测试，但运行它仍需要执行 ctest。

单配置生成器下，测试通过时能看到 score_rules 成功；最后一条命令的标准输出是 lin:82、mei:95，标准错误是 line 3: invalid record，退出码为 1。这表示两行被接受、一行被拒绝。多配置生成器需要在构建和测试时指定同一个配置，例如分别加 --config Release 和 -C Release；可执行文件位于对应配置子目录。

把 /build/、编译得到的可执行文件和本机缓存放入 .gitignore，保留源码、构建文件和运行说明。README 至少让另一个人知道输入约定、构建命令、一个成功样例和一个失败样例。真正起作用的约定，会回答“这次失败怎样被发现”和“换台机器怎样重现”，不只是统一缩进。

小结：把可依赖的行为留下来

课堂代码帮助隔离一个知识点，作业把多个知识点放进同一任务。自己写小项目时，可以沿同一条路径推进：先说明调用者能期待什么，再把输入验证放到结果产生之前，把核心规则从终端和文件中分离，最后用反例固定边界。

不必一开始就搭建庞大的目录。先让一条记录从输入到输出走通；当第二个调用者出现时提取接口，当规则开始变化时留下测试，当文件开始增多时让构建系统记录依赖。代码量增加之前，先让每次修改都有一个明确、可运行的判断依据。
