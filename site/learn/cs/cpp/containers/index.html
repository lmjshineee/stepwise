容器：存下一周温度，为什么还会越界？

从温度记录理解 vector 的元素与容量，再检查遍历、删除和失效边界，用 map 与 set 解决按键查找和去重。

课程C++C++23CS106L容器数据结构迭代器

本篇的学习目标能分清元素与容量、判断修改后的位置是否有效，并按下标、键与取出顺序选择容器。
建议先读引用与初始化

把每天的温度存起来

天气记录每天多一条。若为每一天单独声明变量，求最高温时就得不断修改程序。容器把一组元素放在一个对象里，让同一段代码处理不同数量的数据。

有空位，不等于有元素

想提前留出一周的存储空间，可以调用 reserve(7)。但它没有替你记录七天的温度。把 vector 想成一排可用位置：capacity() 是不必重新分配存储就能容纳的元素数，size() 是现在真正存在的元素数。程序只能访问后者。

reserve(n) 请求容量至少为 n，保留已有元素和数量；resize(n) 把元素数改为 n，缩小时删除末尾元素，增大时添加元素。对本例的 int，新添加的元素为 0。resize(n, value) 则用指定值补齐。

reserve 不承诺容量恰好等于参数，也不会因较小的请求而收缩容量。追加超出当前容量时，vector 会申请更大的存储并迁移元素；标准没有规定必须翻倍。已知总量时可以一次预留，没必要每加一个元素就重新请求恰好够用的容量。

追加元素与修改元素是两件事

values[0] = 18 只会修改第 0 个已有元素，不能创建它。在 C++23 中，对空 vector 这样写属于未定义行为：程序没有可依赖的结果，偶尔没崩溃也不能证明正确。reserve(7) 之后仍然如此。

push_back(18) 才是追加，返回类型为 void，没有可供赋值的返回值。因此 values.push_back(18) = 18 也是错误写法，只不过这次会在编译时被拒绝。想创建三个值为 18 的元素，可以用上一章讲过的 std::vector<int> values(3, 18);；{3, 18} 则是两个元素 3 和 18。

标准模板库（STL）的常用组合是：容器管理元素，迭代器表示位置，算法通过这些位置处理元素。标准库还包含流等其他设施，STL 不能简单当作整个标准库的同义词。迭代器也不等于任意指针；不同容器允许的位置操作不同。

记录继续增长，旧位置还能用吗？

上一章的引用是对象的别名。若先用 int& first = values.front() 记住一个元素，随后容器迁移了元素的存储，旧别名就不能继续使用。它没有“跟着元素搬家”的保证。

修改容器不总是让所有位置失效，关键在于操作：

vector 操作对已有位置的影响
重新分配存储所有元素引用、指针、迭代器及旧 end() 失效
尾部追加且没有重新分配已有元素的位置仍有效，旧 end() 失效
中间插入且没有重新分配插入位置及其后的引用、指针、迭代器失效
删除元素删除位置及其后的迭代器、引用失效，包括旧 end()

不要在范围 for 中一边遍历同一个 vector 一边追加：范围循环会保存遍历边界，即使提前预留了容量，追加也会使原来的尾后位置失效。若必须读旧记录并产生新记录，可以把结果存入另一容器，再处理合并。

删除当前元素后，从返回的位置继续

假设数据为 10、11、12、13，要删掉偶数。erase(it) 删除当前元素，后续元素向前补位，并返回能继续遍历的位置；若删掉的是最后一个元素，返回新的 end()。

删除 10 后，11 补到当前位置；必须继续检查 11。未删除时才前进。如果删完后仍执行 ++it，既可能操作失效迭代器，也可能跳过刚补过来的元素。把返回值赋给 it，就是重新取得有效位置。

选读：其他容器的位置稳定性

失效规则跟着容器与操作走

deque 首尾插入通常不移动已有元素，但仍会使迭代器失效；引用和迭代器不能混为一谈。list 插入不会使已有元素的迭代器和引用失效，删除使被删元素的位置失效。无序关联容器重新组织哈希桶（rehash）时，迭代器失效，指向已有元素的引用和指针仍有效。

这些规则不能由“看起来地址没变”推断。需要长期保存一个位置时，先明确它是否必须跨越插入、删除或重排，再查该容器的具体规则。

按天数、名字还是取出顺序查找？

温度按第几天访问，用 vector 自然；若要按城市名查温度，每次扫描所有名字就不方便了。关联容器按键查找：map<K, V> 保存键和值，set<K> 只保存键。它们都能避免比较等价的键重复出现；multi 版本允许重复键。

map 的下标可能悄悄增加一条记录

std::map<std::string, int>（<map> 与 <string>）把名字关联到整数。readings["lin"] = 18 在键缺失时创建记录，再把值设为 18；键已存在时修改原值。问题在于，只写 readings["mei"] 来查询缺失键，也会创建记录，对本例的 int 值初始化为 0。

只检查存在性时用 contains(key)（C++20），返回 bool，不会插入。已有键取值可用 at(key)（C++11），缺失时抛出 std::out_of_range，也不会插入。若希望一次查找并处理“没找到”，使用 find(key)：成功时返回元素位置，失败时返回 end()。

预期输出：

map 的每个元素是一对键和值，it->second 取得迭代器所指元素的值，等同于 (*it).second；first 是键。if 圆括号里先声明变量再判断的写法自 C++17 引入，把 it 的作用域限制在分支内。循环中的结构化绑定也自 C++17 引入，const auto& 让两个名字只读地指向原元素，避免复制。

默认的 map 按键从小到大遍历，所以先输出 lin，再输出 mei，与插入顺序无关。键必须能按所选比较规则排序；不能在原位置改键来破坏排序。它通常用平衡搜索树实现，标准规定相关操作的复杂度，不要求必须是红黑树。

组织数据，是在给常用操作让路

按下标访问和按值查找是两种任务。vector 可以直接到第 100 个位置，但在未排序的记录中寻找某个名字，最坏要逐条比较。map 维护键的顺序，为按键查找付出额外组织与存储成本；unordered_map（C++11，<unordered_map>）则用哈希把键分到桶中。

哈希可以理解为“由键计算出存放区域的编号”。不同键仍可能进入同一区域，因此还要比较键是否相等，不能把同一个哈希值当成同一个键。无序容器不提供按键排序的遍历，查找平均快，也不保证每次都快；自定义键需要相互一致的哈希与相等判断。

下面用 n 表示元素数：O(1) 表示操作次数不随 n 增长，O(log n) 增长缓慢，O(n) 可能随元素数成比例增长。它们描述工作量的增长趋势，不是毫秒数，也不直接决定一个很小容器的实际速度。

需求先考虑关键取舍
按下标访问、顺序遍历、尾部追加vector<T>下标访问 O(1)；尾部追加摊还 O(1)，单次重新分配为 O(n)
按键查找，同时需要键有序map<K, V>查找 O(log n)，不提供按名次直接访问
按键查找，不需要排序unordered_map<K, V>平均 O(1)，最坏 O(n)，遍历无排序保证
两端频繁增删，同时保留下标访问deque<T>两端增删 O(1)，元素不保证整体连续
只允许先进先出／后进先出queue<T>／stack<T>接口限制取出顺序，不能任意下标访问

“摊还 O(1)”是说连续做很多次追加，总体工作量平均到每次是常数级；不表示每一次追加都同样便宜。连续存储也会让 vector 的遍历更容易利用缓存，因此不能只看查找这一列就断言另一种容器总是更快。

set 用来回答“是否已经出现过”

只想知道某个名字是否出现过，不需要给它附一个温度，可以用 std::set<std::string>（<set>）。insert(value) 尝试加入键；等价键已存在时不再增加元素。contains(value)（C++20）检查存在性，erase(value) 删除匹配的键并返回删除数量。对 set，这个数量只会是 0 或 1。

把它用于重复检测时，insert 的返回值还能同时告诉你是否刚加入新键；不必一定先检查再插入。multiset 保留重复项，按键 erase 可能一次删掉多个；不能把 set 的 0／1 结论套过去。

选读：容器分类与接口速查

分类服务于操作选择

序列容器管理位置和顺序，有序关联容器管理键的比较顺序，无序关联容器用哈希组织键；适配器基于其他容器提供受限的接口。不同分类共享部分名字，例如 size() 与 empty()，不表示它们有相同的存储布局和失效规则。

序列容器：连续、两端与节点

类型及头文件适合什么使用条件与代价
vector<T>，<vector>可增长的连续序列尾部追加方便，中间增删需搬动后续元素
array<T, N>，<array>，C++11编译期确定元素数的连续序列大小固定，没有追加接口
deque<T>，<deque>两端增删、按下标访问整组元素不保证连续
list<T>，<list>已有位置处插入、稳定的其他元素位置找到目标仍可能 O(n)，不支持下标，节点有存储成本
forward_list<T>，<forward_list>，C++11只需向前走的链式序列不支持后退、下标与 size()；删除接口为 erase_after

list 在“已经拿到位置”时插入或删除才是 O(1)，若先遍历寻找那个位置，就还要计入查找成本。它的迭代器不能像 vector 迭代器一样直接加 5。

关联容器：唯一键与重复键

有序的 set／map 保留唯一键，multiset／multimap 允许等价键重复；四种类型分别需要 <set> 或 <map>。判断等价用比较规则：两个方向都不被判为“更小”才算等价，不一定等同于 operator==。

无序系列自 C++11 引入：unordered_set、unordered_map 及它们的 multi 版本，分别使用 <unordered_set>、<unordered_map>。它们依赖键相等和哈希，而不依赖排序。迭代顺序没有保证，不宜把某次输出顺序写进预期结果。

C++23 还引入 flat_map／flat_set 及 multi 版本，分别来自 <flat_map>、<flat_set>。这些有序适配器默认使用 vector 存储，适合读多、集中构建的场景；插入、删除和位置稳定性需要另行比较，标准库支持也需检查。版本更新并不意味着应无条件替换已有容器。

适配器：限制取出顺序

stack<T>（<stack>）后进先出，像一摞盘子；用 push 放入，top 查看最近放入的元素，pop 移除它。queue<T>（<queue>）先进先出，像排队；用 front 查看队首，back 查看队尾。pop 只移除，不返回元素，查看或弹出前要保证非空。

priority_queue<T> 也在 <queue> 中，每次取优先级最高的元素；对默认的整数比较规则，top() 是最大值。它不保留先进先出顺序，也不能据此按序遍历全部元素。这三种适配器不提供通用的 begin()／end() 遍历接口。

把“没有温度”与任意温度值分开

若把求最高温封装成函数，返回 −1 表示空记录会与合法温度冲突。std::optional<int>（C++17，<optional>）表达“有一个整数，或没有值”：std::nullopt 是没有值；判断结果存在后，*result 才能取出整数。

下面是函数片段。std::ranges::max_element（C++20，<algorithm>）接收整个容器，返回最大元素的位置，空容器返回 end()。这把前面的范围概念用于一个现成算法；返回前先确认位置有效。

调用时写 if (auto result = peak_temperature(temperatures); result)，只有分支内才能读取 *result。如果只在 main 中输出最高温，开头那种先检查空记录再遍历的写法已经够用；需要复用的函数接口才值得进一步表达“结果可能缺失”。

小结：数量、位置与查找方式分开判断

先用 size() 判断元素是否存在，再用容量判断追加是否可能重新分配。预留空间不会替你创建元素，end() 也不会因为落在分配区域里就变成可读取的位置。

每次插入、删除或扩容之后，重新检查保存的位置是否有效；erase 的返回值是继续遍历的依据。选容器时，再问常用操作是按下标、按键，还是按取出顺序，连同定位、搬移和存储成本一起比较。
