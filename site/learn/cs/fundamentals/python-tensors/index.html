NumPy 与 PyTorch：形状、视图和数据搬运

在真实 NumPy 和 PyTorch 张量上检查 shape、stride、共享存储与复制边界。

教程AI InfraPythonmixed
开始自测
建议先读读懂 AI 工程代码向量与矩阵

一个数组转置后，数值没有复制，shape 却改变了；改动转置后的元素，原数组为什么也变？这和普通列表浅复制相似，但还多了 shape、stride 与设备等信息。

本篇使用真实 NumPy 与 PyTorch CPU 张量。数学含义先读矩阵一篇，这里集中解释实际 API、共享关系和数据搬运。

数据地址还不够描述一个张量

一个二维数组可以看成底层存储，加上 shape、dtype 和定位元素的步长。PyTorch 张量还包含 device 等信息。shape 说每个轴多长，dtype 说怎样解释每个元素，stride 说索引增加一步时跨过多少存储位置。

把 [0,1,2,3,4,5] 按 2×3 解释：第 (1,0) 个元素在偏移 3。元素步长为 (3,1)，定位公式是 3*i+j。NumPy 的 .strides 以字节为单位，PyTorch 的 .stride() 以元素为单位，比较时必须先统一单位。

同样 shape 的两个数组，可能一个连续、一个隔行取样；相同值也可能在不同设备。仅打印 shape 还不能判断一次操作会否复制，或访问是否连续。

转置改了读法，没有自动新建内容

2×3 转成 3×2 后，步长变为 (1,3)。现在 (0,1) 仍定位到原数组偏移 3，因此写入 99 会改变原来的第二行第一列。普通独立复制则有自己的存储。

这组转置索引来自固定的六元素数组。NumPy 的字节 stride 要除以 itemsize 才得到这里的元素 stride；实际 API 对照见完整程序。

先在视图中写 99，再重置并建立独立复制后写 99。两条路径都能显示一样的逻辑数值，但写回关系不同。

np.arange(...,dtype=np.float32) 明确创建六个 float32；original.T 是本例的转置视图，original.copy() 是独立数组。torch.from_numpy(original) 在这里让 CPU 张量与该受支持的 NumPy 数组共享存储，因此通过 tensor 修改也会反映回来。

共享有条件，不能把任意 dtype、负步长或任意设备都称为零复制。detach() 也不是复制的别名；它首先改变求导关系，仍可能共享存储。

reshape 与连续化要分别核对

reshape 在能表达为视图时可能共享，否则可能复制；不能只看方法名。PyTorch 的 view 对现有 stride 的兼容性有要求，不保证任意转置后都能得到希望的形状。

在本例中 tensor.T 非连续，调用 .contiguous() 得到独立连续存储，修改新张量不改原 tensor。但本来已经连续的张量调用 contiguous 可能直接返回自己，所以也不能把它当成“永远复制”的保证。若接口确实要求独立副本，应选择明确的复制方式并检查实际语义。

广播省下的输入复制，不等于所有内存成本消失

计算 NNN 个点到 KKK 个中心的平方距离，每个向量有 DDD 个坐标：先把点变成 (N,1,D)，中心变成 (1,K,D)，相减得到 (N,K,D)，再沿最后轴平方求和，输出 (N,K)。

形状合法并不意味着内存合适。若 N=K=1000,D=128N=K=1000,D=128N=K=1000,D=128，仅 float32 差值中间量就有 128,000,000 个元素，约 488 MiB；本验证函数转成 float64，会再增加一倍元素字节数。临时平方结果还可能增加峰值。

批量处理、分块或改写公式可以减少某些中间量，但也要比较误差与计算路径。先估算最大的中间 shape，再决定怎样“向量化”，比直接删掉所有 Python 循环更可靠。

移动设备是数据流的一部分

CPU 和加速设备之间通常需要搬运数据。.to(...) 是否新建结果取决于请求的设备和 dtype 等条件；没改变条件时也可能返回原对象。不要把所有调用都当成实际复制，也不要把需要搬运的转换当成免费类型标签。

数组的逻辑元素字节数与进程实际占用不同：多个视图可共享一块存储，框架会缓存分配，算子可能创建 workspace。把每个视图的 nbytes 都相加，会重复计算共享部分；反过来只看一个输出，也会漏掉临时量。

小结：数学值之外，还要追踪存储与设备

shape 决定索引范围，stride 决定怎样定位，dtype 决定表示，device 决定在哪执行。视图、复制、连续化和设备移动分别改变不同关系；先验证数据与共享语义，再优化分块和搬运。
