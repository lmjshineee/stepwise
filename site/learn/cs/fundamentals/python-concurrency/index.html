并发与异步：等待、计算和背压

分别处理等待与计算，用有限队列、任务组和总超时约束异步任务并验证取消。

教程AI InfraPythonpractical

建议先读读懂 AI 工程代码数据怎样喂给模型

四个请求都在等待外部结果，顺序处理会把等待时间相加；开无限多个任务又可能把队列、连接或内存撑满。并发的目标是利用可重叠的时间，同时保持工作量、失败和退出可控。

本篇分开讨论等待与计算。时间线是固定排程示意，下载程序则真正运行 asyncio、线程和 spawn 进程；等待样例没有调用模型，也不能用来声称模型推理加速。

先判断谁在工作，谁在等待

同步调用要等当前操作返回，才继续下一步。线程允许同一进程内多个执行流共享地址空间；进程拥有独立运行环境，传入数据往往要序列化或借助专门共享机制。async/await 则通过协作暂停，让一个事件循环在任务等待时切换到其他任务。

async def 定义协程函数，不会把里面的任意代码自动变成并行计算。大段普通 Python CPU 循环如果不让出执行，会堵住事件循环；阻塞式网络或磁盘调用也不能因为放在 async 函数里就自动异步。

工作类型可以先试什么要核对的代价
可异步等待的 I/Oasyncio 加有限并发库是否真正异步、取消和超时
阻塞式 I/O 接口适量线程共享状态、线程数量与超时
普通 Python CPU 密集计算多进程或改写热点启动、序列化、任务颗粒度
原生数值算子先测库自身行为是否释放 GIL、内部线程与过度订阅

普通带 GIL 的 CPython 与自由线程构建不能混为一谈；原生数值库也可能释放 GIL。先知道实际解释器和库在做什么，不背“所有 Python 线程都没用”的结论。

任务变多，不等于可同时运行的位置变多

四个任务均在时刻 0 就绪，按顺序分配最早空闲槽位。这是固定排程示意，不模拟操作系统、背压或 GPU；有界队列与取消由下载程序实际验证。

这是非抢占、按顺序分配最早空闲槽的教学模型。真实操作系统、网络竞争、任务依赖与设备调度都可能改变轨迹。图中没有模拟有界缓冲，下面的真实代码才负责这一契约。

有界队列让生产者也承担等待

本实验区分两个上限：worker 数控制同时执行多少任务，队列 capacity 控制内部最多缓冲多少个尚未领取的任务。await queue.put(item) 在队列满时暂停生产者，这就是一种背压。

它不意味着整个输入只占 capacity 个元素。本项目先将延迟样例转换为列表，公开输入本来就很小；真实无限源还须在输入读取处保持惰性，不能在有界队列前先堆一个无限列表。

worker 领取元素后，在 try/finally 中保证 task_done()；真正执行期间增加 active，离开这段范围时再减少。结果按任务身份记录，不能靠完成顺序假设输入顺序。

超时后要结束任务，而非只停止等结果

最后回到 run_jobs 的外层，把生产者和有限 worker 放进统一范围，再交付结果：

TaskGroup 和 asyncio.timeout 自 Python 3.11 引入，本项目基线为 3.12。整个任务组置于 timeout 范围。一个 worker 抛错时，TaskGroup 取消其他成员并等待清理完成；多个错误可能以 ExceptionGroup 汇总。超时也应真正清理组内任务，避免请求已经失败，后台还在继续占用资源。

因此测试不仅检查“抛出 TimeoutError”，还比较调用前后的活动任务集合；故意令一个 worker 失败时，也检查其他 worker 已结束。代码在正确的 finally 中做计数和队列清理，而不是把异常吞掉并伪造成功结果。

取消是协作式的。如果协程卡在不让出控制的 CPU 代码中，timeout 不会像硬件中断一样立刻抢走执行权。必须为阻塞计算选合适的执行方式，并理解跨线程或进程取消的边界。

小结：限制在途工作，明确失败后的责任

并发利用可重叠的等待或多个执行资源，async 并不自动提供 CPU 并行。把输入缓存、排队容量、运行数量和结果保存分别计入预算；发生超时或错误后，确认相关任务真正结束，再谈可靠吞吐。
