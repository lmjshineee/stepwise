数据怎样喂给模型：迭代、生成器与批处理

把 JSONL 逐条转换为可控批次，保留尾批次，按 mask 汇总有效数据并关闭资源。

建议先读读懂 AI 工程代码NumPy 与 PyTorch

把所有样本读入一个列表，代码很直观，却可能在第一次计算前就占满内存。换成生成器也不自动解决全部问题：谁还在缓存、batch 多大、提前停止后文件是否关闭，都需要沿数据流检查。

本篇把公开的变长数字样本逐行读入、组批、填充，再正确汇总有效元素。它为后续 DataLoader 或模型输入准备一条可以独立测试的参考路径。

生成器交出一项，不替你保存全部历史

普通函数 return 一个结果后结束；生成器在 yield 处暂停，下一次请求元素再继续。文件逐行读取因此可以只保留当前记录。但下游若写 list(generator)，仍会一次保存所有元素，惰性优势就消失了。

本项目每行是一个 JSON 数字列表。JSON 解析成功后继续验证类型与有限性，错误带上行号。这里允许空列表表示无有效元素的一条记录，最终汇总再明确处理零计数；不能让接口一会儿把空当错误，一会儿当数值 0。

组批既要保留尾批，也要换一个容器

batch_size 是每次交给计算的样本条数，不是每条样本的元素数。三条样本、每批两条，应交出一批两条和一批一条，而不是丢掉最后一个不完整批次。

yield 后重新建立 pending=[]，避免继续填充时改动已交出的外层 batch。这里并没有深复制每条样本，调用者仍需遵守样本共享的约定。实际并发读取还要保证对象不会被另一方意外改写。

填充保持矩形，mask 保留真实含义

样本 [1,2,3] 与 [4] 不能直接组成普通数值矩阵。第一批补成 [[1,2,3],[4,0,0]]，mask 为 [[真,真,真],[真,假,假]]。灰色填充不是额外两个样本，真实数据中也完全可能存在合法的 0。

灰格是填充，mask 为 false；真正数值为 0 的样本仍需计入有效元素，不能用 value!=0 代替 mask。

改变 batch 大小，填充格数会变化，真正的元素和总体均值不应改变。规则由 mask 决定，不能拿 values!=0 代替 mask，否则把合法零值删掉了。

本例从最长样本得到宽度。真实模型还可能要求最大长度、截断或对齐，这些策略必须显式记录；截断不是纯粹改变存储，它会删除输入内容。

累计 sum/count，不平均不等长批次的均值

第一批有效数为 4、和为 10，均值 2.5；最后一批 [5,6] 有效数为 2、和为 11，均值 5.5。直接平均两个均值得到 4，是错的。全局正确值是 (10+11)/(4+2)=3.5(10+11)/(4+2)=3.5(10+11)/(4+2)=3.5。

只在最终有有效元素时计算均值。零计数返回缺失状态，由调用者决定展示或拒绝；不要为方便图表填一个假零。这个原则与概率中的加权统计一致，但不直接替代具体模型 loss 的所有归一化约定。

提前退出时也要结束资源范围

生成器暂停在文件的 with 内时，文件可能仍打开。仅仅在外层 break，不应被当成所有解释器和引用关系下的即时关闭保证。本例用 contextlib.closing 管住生成器，正常结束、早停或异常都按范围调用 close。

预取把一些未来元素放进缓冲，以便重叠等待和计算，但缓冲容量也决定额外内存。先把同步语义与释放边界验证正确，再进入有界队列，而不是一开始就增大 worker 数来掩盖数据错误。

小结：数据流要同时管理数量与寿命

生成器控制何时产生元素，组批控制计算颗粒度，mask 控制哪些元素有效，sum/count 控制统计权重，资源范围控制何时释放。性能优化应保留这些约定，否则吞吐提升可能只是漏了数据、尾批或错误。
